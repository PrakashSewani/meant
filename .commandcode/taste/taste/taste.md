# Taste

- Wants the agent to act as a critical thinking partner — challenge assumptions, surface weaknesses and better alternatives, and rethink the idea where it can be materially improved — rather than literally implementing the brief as written. Confidence: 0.9
- Treats their own wording, terminology, and early name/naming ideas as open to revision ("do not assume my wording... is correct"). Confidence: 0.85
- When the agent surfaces open questions, expects it to also state its own recommended answer and make the call ("suggest something") rather than bounce decisions back to them. Confidence: 0.6
- Frames requests at a product/strategy level (thesis, positioning, differentiation, UX) and expects the agent to think like a product strategist and designer, not just execute features. Confidence: 0.7
- Prefers AI integrations to be provider-agnostic and BYOK (bring your own key) — deliberately not tied to a single AI company or model. Confidence: 0.9
- Wants shipped option lists to come with an escape hatch: any surface or config offering presets should also let them enter their own values (e.g. a custom OpenAI-compatible endpoint with base URL and model ids alongside the provider presets), rather than being limited to the fixed choices. Confidence: 0.8
- Expects new projects to interoperate with the config formats of tools they already use (e.g. OpenCode, Claude Code). Confidence: 0.65
- Expects documentation and agent scaffolding to be created proactively for a new project — README.md, AGENTS.md, and organized `docs/` — not just code. Confidence: 0.75
- Wants the agent to research the internet for relevant knowledge and to create/reuse reusable skills (playbooks) for the work. Confidence: 0.6
- Treats privacy and user control as fundamental design requirements, not afterthoughts. Confidence: 0.7
- Keeps configuration/secret surfaces strictly separate from in-page UI: BYOK keys, providers, models, and general settings live in the extension's own surfaces (popup/options page), while in-page/inline surfaces (e.g. the Register Bar) stay free of config controls — they may deep-link to settings but must never embed a config form. Confidence: 0.75
- Wants a runnable, ready-to-load build artifact so they can test/dogfood the product themselves (e.g. "produce a build for me to test") — expects work to end in something they can actually run, not just code and tests, and will personally load it and report what breaks. Confidence: 0.75
- Sequences work as spec-then-build: wants decisions and docs written up and committed as their own step before implementation starts, and expects the agent to flag any remaining exploration/risks ("or do you want to explore more") rather than silently jumping into code. Confidence: 0.6
- Expects implementation in TypeScript ("typescript ofc") with a deliberately organized folder structure — e.g. a pnpm workspace split into separate packages (core, config, adapters, ui) and an app — rather than a flat repo. Confidence: 0.7
- Wants tests and CI workflows set up as part of the initial scaffold, not bolted on later (explicitly asks for "tests and workflows" when kicking off implementation). Confidence: 0.7
- Favors phased/staged delivery: ship the simple, self-contained version first and defer heavier infrastructure (accounts, login, cross-device sync, a hosted tier) to "a much later step," gated on the product proving traction. Confidence: 0.65
- Strongly prefers minimal-friction onboarding over granular, repeated setup: wants broad permission granted once at install/enable time (e.g. "if the user agrees, enable on all sites when you first install and ask for permission") rather than enabling scope one site/one item at a time, which they call "stupid". Granular control can remain as an option, but the default should be one prompt. Confidence: 0.85
- Expects user-facing actions to never fail silently: if an action does nothing or a prerequisite is missing, the UI must surface it (feedback message, badge, notice) instead of a silent no-op that is indistinguishable from a broken product. Confidence: 0.7
- Cares about visual polish of the UI surfaces and will call out styling that needs "touchup"; when giving feedback on looks, expects a targeted pass on the specific surface named rather than a little polish spread everywhere. Confidence: 0.6
- Expects the agent to visually verify its own UI work — to open a real browser, take screenshots, and look at the rendered result ("enable vision and open a test agent browser of yourself, see for yourself") — rather than trusting that passing tests mean the UI is correct. Confidence: 0.8
- Prefers in-page surfaces to be lightweight overlays anchored to the user's context — appearing next to the selection like a right-click/context menu, hugging their content — rather than a full-width panel pushed into the page's DOM/layout. Confidence: 0.75
- Wants remote/paid API calls to be user-initiated, never fired automatically: an action surface should show what it inferred and wait for an explicit confirm (e.g. a Transform/Accept action) before any provider request is sent, and changing config should return to the "asking" state rather than re-firing on its own. Confidence: 0.75
- Prefers controls to be visible by default rather than hidden behind a disclosure/dropdown: hiding the product's core options behind a chevron is the wrong default (they explicitly call this out: "keep options open by default do not keep them in a dropdown"). Confidence: 0.8
- Expects a distinct, visible in-progress/loading state — a spinner/working label and placeholder content — and rejects relying solely on a dimmed or disabled action button as the only signal that something is happening. Confidence: 0.75
- Prioritizes functional correctness over visual polish in the current phase: when features are broken, wants those fixed first and is content to defer UI work ("lets revert... we will improve ui later") rather than block on looks. Confidence: 0.6
- When a change appears to make output worse, reaches for reverting to the previous known-good version (e.g. "revert to previous prompt") instead of debugging forward in the regressed state. Confidence: 0.55
- Expects user-supplied inputs to actually drive the model's output, not just be passed as neutral context: filling in a field like the audience ("who is reading this") should make the output address that person (by name where the format calls for it), rather than merely labelling the text. Confidence: 0.6
- Takes personal ownership of the visual design language ("I will rework that on my own") while still demanding functional correctness from the agent; values the UI being factored into small, separable, restylable components so they can rework the look independently of behavior. Confidence: 0.6
